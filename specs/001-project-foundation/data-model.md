### 1. User

Represents a registered user account. This is the only domain table created in the
foundation migration.

| Column          | Type           | Constraints                              | Notes                                                                                 |
| --------------- | -------------- | ---------------------------------------- | ------------------------------------------------------------------------------------- |
| `id`            | `uuid`         | PRIMARY KEY, default `gen_random_uuid()` | Uses PostgreSQL's native UUID generation; no application-side UUID dependency needed  |
| `email`         | `varchar(320)` | NOT NULL, UNIQUE                         | RFC 5321 maximum email length; unique index enforced by the DB                        |
| `password_hash` | `varchar(255)` | NOT NULL                                 | Stores Argon2id hash. Length 255 is sufficient for all current Argon2 encoded outputs |
| `created_at`    | `timestamptz`  | NOT NULL, default `now()`                | Stored in UTC; `timestamptz` ensures correct timezone handling                        |
| `updated_at`    | `timestamptz`  | NOT NULL, default `now()`                | Updated by application on every write; a DB trigger may be added in a later migration |

**Indexes**:

- Primary key on `id` (implicit)
- Unique index on `email` (implicit from `UNIQUE` constraint)

**Validation rules** (enforced at the application layer via Zod before DB write):

- `email`: valid email format, max 320 characters, lowercased before storage
- `password_hash`: non-empty string; must be produced by the password-hashing service
  (never the raw password)

**State transitions**: None in this epic — user records are created only.

**Security note**: `password_hash` must never be returned in any API response or
written to any log. The logger redaction list covers the `password` key pattern
which does NOT cover `password_hash` — the API serialiser must explicitly exclude
this field from every response shape.

### 2. Migration Record (`schema_migrations`)

An internal tracking table managed by Drizzle Kit. Developers should not write to
this table directly.

| Column       | Type          | Constraints               | Notes                                                                    |
| ------------ | ------------- | ------------------------- | ------------------------------------------------------------------------ |
| `id`         | `serial`      | PRIMARY KEY               | Auto-increment                                                           |
| `hash`       | `varchar(64)` | NOT NULL, UNIQUE          | SHA-256 hash of the migration file content; used for checksum validation |
| `created_at` | `timestamptz` | NOT NULL, default `now()` | When the migration was applied                                           |

**Note**: Drizzle Kit manages this table automatically. The schema above is for
documentation purposes. The actual DDL is generated by `drizzle-kit migrate`.

### 3. Job (BullMQ — Redis, not relational)

Jobs are stored in Redis by BullMQ. They are not persisted in PostgreSQL. This entity
is documented here for completeness; it has no Drizzle schema.

| Field           | Type             | Notes                                                            |
| --------------- | ---------------- | ---------------------------------------------------------------- |
| `id`            | `string`         | UUID assigned by BullMQ                                          |
| `name`          | `string`         | Job type name (e.g., `health-check`)                             |
| `data`          | `object`         | Job payload (JSON-serialisable)                                  |
| `opts.attempts` | `number`         | Max retry attempts                                               |
| `opts.backoff`  | `object`         | Backoff strategy (`exponential`, delay)                          |
| `status`        | `enum`           | `waiting \| active \| completed \| failed \| delayed \| stalled` |
| `timestamp`     | `number`         | Unix ms when enqueued                                            |
| `processedOn`   | `number \| null` | Unix ms when worker started processing                           |
| `finishedOn`    | `number \| null` | Unix ms when completed or failed                                 |

**For this epic**: Only a `health-check` job type is registered (FR-008). Its payload
is `{}` (empty object). Its sole purpose is to verify the worker is connected and
processing jobs.

## Drizzle Schema (TypeScript)

```typescript
// src/lib/db/schema.ts
import { pgTable, uuid, varchar, timestamptz } from 'drizzle-orm/pg-core';
import { sql } from 'drizzle-orm';

export const users = pgTable('users', {
  id: uuid('id')
    .primaryKey()
    .default(sql`gen_random_uuid()`),
  email: varchar('email', { length: 320 }).notNull().unique(),
  passwordHash: varchar('password_hash', { length: 255 }).notNull(),
  createdAt: timestamptz('created_at').notNull().defaultNow(),
  updatedAt: timestamptz('updated_at').notNull().defaultNow(),
});

export type User = typeof users.$inferSelect;
export type NewUser = typeof users.$inferInsert;
```

## Migration Files

Migration files live in `src/lib/db/migrations/`. Drizzle Kit generates them from
the schema; developers MUST NOT hand-edit generated files.

```text
src/lib/db/migrations/
├── 0001_create_users.sql       ← generated by drizzle-kit generate
└── meta/
    ├── _journal.json           ← migration journal (Drizzle internal)
    └── 0001_snapshot.json      ← schema snapshot
```

The migration runner (`src/lib/db/migrate.ts`) is called at application startup
(before the HTTP server binds) and at worker startup. It uses `drizzle-orm/migrator`
with a PostgreSQL advisory lock (`pg_advisory_lock(1)`) to prevent concurrent
migrations (spec edge case 3).
